## 1. Executive Conclusion

A fundamental architectural mismatch in workload generation was discovered between the IEEE TNSE 2025 paper specification and the codebase implementation.

- **Current Codebase Implementation (`src/data_loader.py`, `train.py`, `evaluate.py`)**:
  Generates task counts using `num_generated = min(EnvConfig.MAX_N, max(1, int(rng.binomial(num_ed, arrival_rate))))`. This imposes a **global bottleneck of $\le 5$ tasks total per slot across all 25 End Devices combined**.
  - Expected total tasks per slot: **~5.00 tasks/slot** ($\approx 0.20$ tasks/ED/slot).
  - Total tasks generated over 300 slots: **1,500 tasks**.
  - Impact: With 25 EDs and 5 Edge Servers (MESs), the edge servers were severely underloaded (~1 task per MES per slot). This explains why previous evaluation runs observed an artificially high ~98% offloading ratio and near-zero queue congestion.

- **Paper Mathematical Formulation (`IEEE TNSE 2025, Eq. 19g & Sec. III`)**:
  Explicitly defines $|m_i^t| \le Max_n = 5$ as a **per-ED maximum** task count generated by **End Device $i$** ($i \in \{1, \dots, N\}$) at time slot $t$.
  - Expected total tasks per slot ($N=25, Max_n=5, p=0.60$): **75.00 tasks/slot** ($3.00$ tasks/ED/slot).
  - Total tasks generated over 300 slots: **22,500 tasks**.

- **Audit Directives Compliance**:
  Per prompt instructions, **no code modifications** (`src/data_loader.py`, `src/config.py`, `train.py`, `evaluate.py`, `run_experiments.py`) have been made. This report provides the full evidence, mathematical diagnostics, ambiguity analysis, recommended fix, affected files, and verification test requirements.

## 2. Current Code Behavior Analysis

### 2.1 Code Trace & Bug Identification
In `src/data_loader.py` (line 164), `train.py` (line 96), and `evaluate.py` (line 38):
```python
# CURRENT IMPLEMENTATION IN CODEBASE:
num_generated = min(
    EnvConfig.MAX_N,
    max(1, int(rng.binomial(num_ed, arrival_rate)))
)
```

### 2.2 Detailed Execution Trace
1. `rng.binomial(num_ed=25, arrival_rate=0.6)` draws a random sample from $\text{Binomial}(25, 0.6)$, which has a mean of $15.0$ and std of $\approx 2.45$.
2. Because $\text{Binomial}(25, 0.6) \ge 5$ in $>99.9\%$ of draws, `min(EnvConfig.MAX_N, ...)` evaluates to **exactly 5** for almost every single slot $t \in [1, 300]$.
3. The generated 5 tasks are placed in a flat list `slot_task_list` and assigned to EDs via `ed_idx = int(hash(task.task_id) % num_ed)`.
4. Out of 25 EDs, **20 EDs receive 0 tasks per slot**, while 5 EDs receive 1 task per slot.
5. System-wide task arrival rate is capped at 5 tasks/slot system-wide rather than $25 \times 5 = 125$ tasks/slot max.

## 3. Paper Evidence & Mathematical Formulation

### 3.1 Paper Definition of $|m_i^t|$ and $Max_n$
In Section III ("System Model", page 4, lines 313–325):
> *"In the system model, we assume that each ED may generate multiple heterogeneous computing tasks during each time period, with a maximum of $Max_n$ tasks generated in each interval. We use $T_i^t$ to denote the task generated by ED $i$ at time $t$, $T_i^t = \{T_{i,1}^t, \dots, T_{i,|m_i^t|}^t\}$. $|m_i^t|$ is the task number generated by ED $i$, $|m_i^t| \le Max_n$."*

In Section III-D ("Problem Programming", page 6, Equation 19g):
$$\omega < \infty, \quad |m_i^t| \le Max_n, \quad \text{(Eq. 19g)}$$

- Index $i \in \{1, \dots, N\}$ explicitly denotes the End Device.
- $T_i^t$ is the set of tasks generated by **ED $i$** at slot $t$.
- $|m_i^t|$ is the task count generated by **ED $i$** at slot $t$.
- $Max_n = 5$ is a **per-ED maximum**.

### 3.2 Task Arrival Rates (40%, 60%, 80%)
In Section VI-A.2, VI-C.2, and Figure 10 caption (page 14):
> *"(a) and (b) depict the average awaiting task size and its variability for ED and MES under a task arrival probability of 40%. (c) and (d) illustrate the comparisons at task arrival probability of 60%. (e) and (f) represent the comparisons at task arrival probability of 80%."*

The reported rates (40%, 60%, 80%) represent the **task arrival probability / rate parameter $p$** of the stochastic task generation process at each slot.

### 3.3 Alibaba Dataset & Slot Arrivals (Question 9 Audit)
- **Paper Statement (Section VI-A.1, page 10)**:
  > *"Our data are derived from a dataset containing 1523 heterogeneous GPU computing nodes from Alibaba Cloud's cluster... After thorough data cleaning, we obtained 26925 usable heterogeneous GPU production tasks. In the experiments, the system randomly selects tasks from this dataset for the EDs at the start of each time frame..."*
- **Slot Arrival Finding**:
  The Alibaba trace provides real task resource attributes (CPU milli-cores, GPU milli-cores, GPU type $R_{i,k}^t$, task duration). The timestamps in the Alibaba dataset span days/weeks across cluster operations, whereas the simulation models a 300-slot window ($K=300$, 1 second per slot = 5 minutes).
  Therefore, **tasks are randomly/sequentially sampled from the cleaned trace pool to populate stochastic arrivals at each slot $t$**, rather than using raw dataset timestamps directly for slot assignment.

## 7. Categorized Categorization of Facts & Assumptions

### 7.1 Paper-Supported Facts
1. $N = 25$ EDs, $M = 5$ MESs, $K = 300$ slots.
2. $|m_i^t| \le Max_n = 5$ tasks per ED per slot (Eq. 19g, Sec. III).
3. Task generation rate / arrival probability $p \in \{0.40, 0.60, 0.80\}$.
4. Dataset contains 26,925 cleaned Alibaba Cloud production tasks.

### 7.2 Original-Code Evidence
1. Official GitHub repository contains only model structure classes.
2. Data loader and task arrival generator were omitted by the authors.

### 7.3 Implementation Assumptions
1. **Per-ED Binomial Process**: Modeling $|m_i^t| \sim \text{Binomial}(Max_n=5, arrival\_rate)$ per ED is an **explicit modeling assumption** to operationalize the upper bound $|m_i^t| \le Max_n = 5$ with parameter $p$.
2. **Trace Task Sampling**: Tasks are sampled sequentially from the 26,925 cleaned dataset pool for each generated arrival.

### 7.4 Remaining Ambiguities
1. The paper does not specify whether task generation across different EDs in the same slot is statistically independent or correlated. (Assuming i.i.d. per ED is standard practice).

## 8. Recommended Implementation Plan

When approved, the fix will update `generate_reproducible_slot_workload` in `src/data_loader.py` to structure tasks **per ED**:

```python
def generate_reproducible_slot_workload(self, dataset_split='test', seed=42, num_ed=EnvConfig.NUM_ED,
                                         total_slots=EnvConfig.TOTAL_SLOTS, arrival_rate=0.6):
    """
    Generates deterministic 300-slot task workload structured PER ED according to:
    |m_i^t| ~ Binomial(Max_n=5, arrival_rate) per ED i in {1..N}.
    EXPLICIT ASSUMPTION: Binomial per-ED arrival process (Paper Eq. 19g).
    """
    df = self.train_df if dataset_split == 'train' else self.test_df
    rng = np.random.RandomState(seed)
    
    workload_by_slot = {}
    task_pointer = 0
    num_tasks = len(df)

    for t in range(1, total_slots + 1):
        slot_workload = {}
        for ed_id in range(num_ed):
            num_generated_ed = rng.binomial(EnvConfig.MAX_N, arrival_rate)
            ed_task_list = []
            for _ in range(num_generated_ed):
                row = df.iloc[task_pointer % num_tasks]
                task_pointer += 1
                t_obj = LRMATask(
                    task_id=f"{row['task_unique_id']}_ed{ed_id}_slot{t}",
                    arrival_slot=t,
                    cpu_milli=row['cpu_milli'],
                    gpu_milli=row['gpu_milli'],
                    gpu_spec=row['gpu_spec'],
                    duration=row['duration']
                )
                ed_task_list.append(t_obj)
            slot_workload[ed_id] = ed_task_list
        workload_by_slot[t] = slot_workload

    return workload_by_slot
```
